# 小程序原粮入厂：首批实施方案

状态：业务范围已确认，实施方案与工作量待评审。2026-11-09。

## 目标与边界

首批让库管、门卫使用小程序接入真实后端，完成原粮入厂的现场环节，并由少量员工现场试用。登记、目测、卸粮确认、关联磅单、开证和审批由库管办理；门卫查询、核验并确认车辆实际出厂。覆盖化验和目测物料，以及正常接收和拒收退厂。

化验录入及确认、生效化验选择、地磅称重和正式磅单生成继续使用现有系统。司机不使用小程序。首批不建设其他业务、仓库档案、库存账、微信身份绑定、扫码、离线审批或离线放行。卸粮地点沿用编号或名称文本。现场以基本有网为前提，磅房本地离线称重和联网后同步仍遵循既有流程。

## 现状与差距

- 小程序已有页面骨架、统一请求层、本地会话和 Mock；真实账号登录及业务尚未接入。配置的 API 地址仍为占位值，生产构建禁用 Mock。详见 [小程序 README](../../miniprogram/README.md)。
- 后端已有账号密码登录、会话撤销、流转单、目测、卸粮、磅单候选及关联、出门证、拒收依据和确认出厂接口；细节以现有实现和 Swagger 为准。会话有效期由服务端配置，基础配置为两小时，不能把保持登录理解为永久有效。
- 流转单现有阶段不完全等同于库管可办理事项，不能先分页再在客户端筛选充当完整待办。正常出门证与拒收记录也是两个分页接口；门卫统一待办需要服务端提供正确的统一筛选、排序和分页，或提供等价的可靠契约。
- 原粮业务现有服务端检查岗位菜单权限，但尚需增加按员工分配厂区的数据范围，并覆盖电脑端使用的同一业务能力。
- 基础工程静态验证已有通过记录；开发者工具运行截图、可靠日志及真机验证仍待完成，详见[基础工程验收记录](../../miniprogram/docs/acceptance/foundation.md)。

## 产品与流程

### 登录与工作台

使用现有员工账号密码；会话有效时保持登录，退出或会话失效后重新登录。工作台根据实际岗位显示库管、门卫入口；同一人员有多个岗位时可进入相应工作区。服务端继续校验权限。

一级页面底部导航为“工作台、我的”，岗位通过工作台切换；登录和业务详情等页面不显示底部导航。

库管工作台使用一份统一列表，不按事项分类；同时支持流转单查询和登记。从登记到实际出厂，未完成的车辆都留在列表中，包括等待化验、等待磅单同步和等待门卫放行；每条记录显示真实状态和下一步。需要库管办理的事项包括目测、卸粮、关联磅单、开证和审批；等待中或依据失效时说明原因，不伪装成可继续办理。页面展示厂区、车牌和当前阶段；现场通常同时只有两三辆车，但系统不按此设置数量上限。

### 库管办理

登记选择厂区、物料并填写车牌，供应商可待核实；司机、合同等字段按既有契约办理。涉及供应商核实或登记更正时复用现有规则，不另造跳过校验的入口。

目测物料由库管记录通过或拒收及必要说明；化验物料等待现有端完成并指定生效化验。接收后，在现场首磅和卸粮完成时填写实际卸粮地点并确认；正式磅单联网同步后，核对候选并关联。条件满足后分别开具和审批出门证；审批不等于实际出厂。校验失败、失效依据与时间冲突展示后端原因。

### 门卫办理

待出厂入口统一展示已审批的正常出门证及有效拒收依据，按车牌或流转单查询；同车多趟必须由门卫选择具体记录。详情清楚标明厂区、车牌、正常或拒收类型及对应依据。门卫核对现场车辆并在实际放行时确认；已出厂记录可查询，不能再次作为待放行事项。确认前由服务端重新校验状态、依据和权限。

### 网络与状态

覆盖加载、空列表、失败、重试和会话失效。写操作遇到超时或断网时提示结果待核实，恢复后重新查询服务端状态，避免把未知结果当失败并重复提交；依据现有版本和幂等规则处理并发及重复操作。不同设备的数据以服务端为准。

## 厂区授权配套

管理员为员工分配一个或多个可访问厂区；未分配的非管理员不能办理受限原粮业务。`ADMIN` 默认可跨厂区；限制同时适用于小程序与电脑管理端，并由服务端落实，不能仅做页面筛选。上线前由管理员逐人分配。

实施设计需覆盖授权的配置入口和审计、列表和详情、创建与更正、操作命令、候选磅单等相关访问路径，核查厂区变更和历史数据；不得因部署顺序阻断现有人员。先准备授权配置和人员名单，再启用限制并验证，具体上线切换和回退步骤在实施时确定。独立化验单是否一并受限、授权调整何时生效尚未确认，不在本方案中预设；这些问题需在相关实现前确定。

## 实施顺序与验证

1. **联调基础**：核对登录响应中的 Token 格式与现有请求层，接通真实 API、会话恢复、退出和错误处理；检查 HTTPS、微信合法域名与环境配置。验证实际登录、过期、退出及多请求失效。
2. **后端配套**：梳理厂区授权及配置入口，补充库管待办和门卫统一待出厂查询契约；完善服务端筛选、排序、分页及授权，更新接口文档和迁移。验证不同厂区、跨厂区直访、待办分页、阶段变化与电脑端兼容。
3. **库管工作区**：实现登记、查询、详情、目测、卸粮、磅单关联和开证审批，复用后端状态规则。验证化验与目测正常路径、目测拒收、前置条件不满足和失效依据。
4. **门卫工作区**：实现统一待出厂、查询、依据核验和实际出厂确认。验证正常、化验拒收、目测拒收、同车多趟、已出厂及重复确认。
5. **完整联调与现场试用准备**：与现有电脑端、地磅数据同步联调，验证关键冲突、断网与超时后的状态恢复；在微信开发者工具取得当前代码截图和运行日志，并在真机核对操作、安全区及网络。两个岗位范围都可用后组织小规模试用。

执行顺序允许局部并行，但首次现场试用以两个岗位的完整流程可用为目标。每次小程序代码任务执行构建及相应检查；Go 与电脑端改动分别执行仓库约定的检查。涉及数据库时提供 migration 并验证。截图、IDE 日志或真机证据缺失时对应项标为待验收，不以构建通过替代。

## 粗略工作量

按一名熟悉项目的全栈开发者估算，单位为人日，不代表交付日期；以下包含必要开发和自动化验证，不含外部等待：

| 工作 | 估计人日 |
| --- | ---: |
| 真实登录、环境配置及基础联调 | 2–3 |
| 厂区授权、电脑端配置与兼容 | 4–6 |
| 待办查询契约与门卫统一列表 | 2–3 |
| 库管和门卫小程序页面及业务接入 | 5–8 |
| 跨端联调、异常验证和试用准备 | 3–5 |
| **合计** | **16–25** |

估计假设现有后端接口及业务规则总体可复用，厂区授权不扩展成通用数据权限平台，现场具备可用账号和业务数据。开发者工具跨宿主通道、真实 HTTPS/微信合法域名、地磅数据同步或厂区历史数据若需要额外整改，会增加时间；并行投入也不等于日历工期线性缩短。完成技术细化后重新估算。

## 首批验收重点

- 库管与门卫分别使用真实员工账号完成岗位操作，厂区范围在服务端生效。
- 分别跑通化验接收、化验拒收、目测通过、目测拒收；正常出厂需有效磅单和已审批出门证，拒收退厂不要求正常出门证及完整磅单。
- 多趟同车能够正确选择；已出厂、依据失效、并发修改、重复操作和请求结果未知时均能正确反馈与恢复。
- 电脑端继续支持同一流程；已配置厂区的员工能正常工作，未经授权的跨厂区访问被拒绝。
- 记录当前代码的微信开发者工具运行截图、日志及真机验证结果，留存未通过项，不以模拟器代替真机。

相关业务规则以[管理端现有实现](grain-intake-implementation.md)和[物料检验方式与流转约定](material-inspection-method.md)为准；本方案不改变磅房离线同步边界或已知同步滞后限制。
