# 原粮入厂一期：业务模型与建设边界

状态：开发规格草案，2026-11-06。本文描述目标行为，不表示功能已经实现或通过验收。

业务依据：`../next/酒厂原粮采购入厂验收业务流程与规则梳理.md`（相对仓库根目录），V2.1，2026-11-06。该文件位于相邻工作目录，不随本仓库分发；本文提取一期核心规则。业务范围变更需同时核对原方案。

配套文档：[状态流转](grain-intake-state-machine.md)、[厂云协同接口](grain-intake-collaboration-api.md)。现有磅单同步继续遵循[厂云同步契约](cloud-sync-contract.md)。本文新增的接口及字段均为草案，不改变现有协议。

## 1. 一期范围

打通库管接车、化验、首磅、卸粮确认、回磅出单、库管开具审批出门证、门卫确认出厂。另支持化验拒收后门卫直接核验退厂。

- 小程序：库管登记、确认实际粮仓及卸粮、开具审批；门卫核验和确认出厂。
- 管理端：采购维护供应商；库管维护粮仓、查台账；化验员录入和确认检测结果。
- 现有地磅端：库管人工确认称重，生成打印正式磅单，回传关联结果。
- 司机无需使用小程序，门卫不登记送粮，不新增硬件。
- 合同编号选填；不建设合同匹配、完整库存、财务、无人值守、取消送货退厂、审批后及出厂后联动更正。

## 2. 当前实现与复用边界

已核对 `server/internal/weighbridge/` 与 `web/src/config/routes.tsx`：当前具备物料、往来主体、厂区、磅单查询、统计和厂云同步；往来主体含公司/个人、供应商身份和信用代码；`TicketSnapshot` 含重量与净重调整字段。源码已有 v4 摘要同步，不能据此推定厂端已对接或已部署。

新增原粮业务应在现有模块化单体内按业务内聚实现，复用认证、基础资料、审计与响应规范。具体 Go 包和表结构在实现时确定，不引入工作流引擎或额外服务。

本趟记录在界面称为“流转单”。本趟记录独立于磅单：登记时尚无磅单，拒收时也不要求磅单。不得把未完成送粮任务伪装成已出单快照上传。

## 3. 业务对象

以下为逻辑字段，尚不是数据库 DDL 或完整 API DTO。

| 对象 | 核心内容 | 约束与归属 |
| --- | --- | --- |
| 本趟记录 | 本趟编号、厂区编码、车牌、粮种、供应商核实状态、司机姓名电话、可选合同编号备注、登记人及时间、流程状态、版本 | 云端创建；同车再次送粮另建一趟；登记时间不当作实际入厂时间 |
| 供应商关联 | 往来主体编码、核实状态、接收时名称和身份快照 | 复用供应商主体；未匹配允许登记，正式接收前必须明确供应商；供应商与司机分开 |
| 化验记录 | 本趟编号、检测次数、水分、杂质、检测人及时间、系统建议、接收/拒收结论、拒收或偏离建议原因 | 历次保留；本趟只有一个最终有效结果；首磅前确认 |
| 扣减依据 | 有效化验记录、规则版本、检测值、扣减比例、计算与取整依据 | 化验阶段固定比例依据；回磅取得净重后才能形成扣减重量；标准待客户提供 |
| 称重关联 | 本趟编号、首磅确认依据、毛重及时间、正式磅单厂区编码与单号、有效状态、皮重与重量结果 | 厂端为称重与正式磅单权威；云端关联，不直接修改厂端单据 |
| 粮仓 | 厂区、编号、名称、启用状态 | 库管维护；建议编号在厂区内唯一；停用不影响历史 |
| 卸粮确认 | 本趟编号、实际粮仓、确认人及时间 | 一车一个实际粮仓；首磅后确认，回磅前必须完成 |
| 出门证 | 本趟编号、证号、开具及审批人员时间、审批所依据的业务版本 | 正常收粮使用；同一库管可开具并审批；是否合并为一次操作待页面设计确定 |
| 出厂记录 | 本趟编号、正常/拒收依据及其版本、门卫、确认时间 | 两条路径共用；每趟仅成功确认一次出厂 |
| 更正记录 | 变更对象、原因、前后内容、操作人及时间 | 一般供应商/粮仓归属更正留痕；影响有效化验或已出磅单的更正不能只改单边 |

本趟编号对外稳定且不可重用，具体编码格式待实现确定；不将车牌或双方内部数据库主键用作跨端关联键。一个本趟记录对应一次送粮，多次检测、一份最终有效检测结果、一组有效两次称重、一份正常出门证或一份有效拒收依据、一条出厂记录。

供应商公司使用统一社会信用代码，个人使用完整身份证号识别、防重复建档。新增个人证件字段，不能默认为现有 `creditCode` 已满足个人身份规则。证件明文仅供有核对权限的岗位查看，普通列表和日志不展示完整号码；现有全量资料同步不默认新增下发身份证。

## 4. 必须保持的业务规则

1. 库管登记车牌、粮种；供应商未明确时标记待核实。保存后化验室可见。
2. 化验员最终决定接收或拒收；系统建议不构成硬性拒收。偏离建议要有原因，拒收要有说明，不增加额外审批。
3. 一期主要落实水分扣减，杂质先记录；同粮种全厂统一规则，不依赖合同编号。
4. 有权限的化验员可复检，保留历史；首磅前完成最终有效结果确认。本地离线称重不以云端在线锁定为前提；恢复联网后通过称重时间和使用的化验依据核对一致性，冲突不得自动覆盖。
5. 首磅后可预指定粮仓；回磅依据必须是现场确认的实际粮仓及卸粮完成，预指定不能代替确认。
6. 正常开证必须同时满足：实际粮仓已记录、卸粮已确认、两次称重完成且磅单有效。
7. 化验拒收不经过库管开证审批、不要求完整磅单；门卫核验有效拒收化验单及说明后确认出厂。
8. 已审批不等于已出厂；门卫在实际放行时确认，一次成功后不得再次使用本趟凭据。
9. 审批后及出厂后更正暂不开放。其他阶段的供应商/粮仓更正须授权并留痕；影响称重使用的业务依据或跨端单据的场景须先确定联动方案，不提供绕过流程的通用编辑接口。

## 5. 数量与统计

- 实际净重 = 毛重 − 皮重。
- 扣减重量按正式水分标准及其取整顺序计算；扣减后重量 = 实际净重 − 扣减重量。
- 按仓收粮以实际净重为主，同时显示扣减后重量，按实际粮种分别统计，不强制粮仓限定粮种。
- 拒收记录保留在流程查询中，不纳入正常收粮台账。未形成有效磅单的在途记录单独展示，不混入已完成数量。
- 只计有效、已关联的收粮磅单；磅单失效须同步影响台账和开证资格。不能把同一重量在本趟记录和磅单中重复累计。
- 收粮累计量不是当前库存；不能直接复用现有最终净重汇总冒充按仓实际净重。
- 重量接口沿用十进制吨字符串、最多三位小数，运算使用整数千分吨。检测值和比例同样避免二进制浮点；其精度、单位和舍入由客户标准决定，不预设比例精度。

## 6. 已确认边界与待确认实施依赖

| 事项 | 已知边界 | 影响与建议 |
| --- | --- | --- |
| 水分标准 | 客户尚需提供基准、区间、公式和舍入顺序；规则配置机制已实现，未提供正式标准前不预置任何数值 | 阻塞正式扣减验收，不能用示例数字补造标准 |
| 化验标准 | 单位、精度、适用粮种、建议验收值待补 | 阻塞字段精度及系统建议；特殊要求线下传达，不设计合同规则 |
| 磅房断网（已确认） | 本地继续称重、出单，联网后同步磅单到云端，再关联对应流转单 | 不以云端在线准备或回执作为本地称重前提；云端未关联有效磅单前不能开证 |
| 厂端与人员身份 | 现有同步无厂端凭据，厂区编码不认证来源 | 新增会推进流程的接口需单独确认来源与人员身份方案，不能只信任传入姓名/编码 |
| 离线时业务依据 | 仍要求首磅前确认最终化验、回磅前完成卸粮确认 | 离线时如何取得化验及扣减依据、现场确认如何传达需细化；不假定云端即时知道首磅，联网后核对时间与版本 |
| 例外与跨端更正 | 审批后、出厂后补正不在一期 | 磅单作废/重开与本趟关联、首磅后纠错需明确，不能绕过阻断自动放行 |
| 粮仓及卸粮内容 | 编号名称和现场确认具体内容待补 | 可先定义必有实际粮仓，确认项不得凭空增加 |
| 小程序登录 | 员工使用现有岗位权限，司机不登录 | 微信身份与员工绑定方式待设计；微信身份本身不授予业务权限 |

接口草案中的技术建议供评审，未标为已确认业务规则。以上问题不阻塞基础对象和正常/拒收路径设计，相关接口正式实现和上线前须解决对应依赖。
