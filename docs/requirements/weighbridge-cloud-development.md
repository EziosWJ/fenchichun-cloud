# 云端过磅业务开发准备

本文是综合管理大平台中云端过磅业务的开发与验证清单，不代表整个平台的开发计划。已确认业务以[云端过磅业务规格](weighbridge-cloud-spec.md)和[厂云同步契约](cloud-sync-contract.md)为准；本地有效规格是本次过磅同步业务字段和例外的依据。下述模块划分和处理方式用于实施设计，接口路径、数据表名称和未定字段不作为双方已确认协议。

> 以下目标以新的厂区编码归属契约为准；云端版本 2 已实现，厂端改造和两端联调尚未完成。

## 当前基础与边界

- 云端已有 Go 模块化单体、PostgreSQL、Goose、用户认证、角色菜单、审计和 React 管理后台。入口在 `server/internal/app`；业务 API 统一 `/api/v1`，响应采用 `{ code, message, data }`。现有用户认证中间件校验用户会话，不等于厂端机器身份认证。
- 云端正在建设过磅、厂区、总部基础资料和厂云同步业务模块；不得把通用字典或部门直接当作物料或厂区。不能由本文件推定本地同步已实现。
- 厂区、物料、往来主体等资料可能涉及平台其他业务；本次只确认其过磅同步所需规则。跨业务复用、归属及其他业务规则尚未确定，不应直接将过磅领域约束推广为整个平台的规则。
- 本次首次上线各厂无历史，正式使用时完成接入并先获得完整资料；不建设历史导入或自动匹配。关闭同步开关后再接入的资料处理遵循[厂云同步契约](cloud-sync-contract.md)；历史单据处理另行确定。
- 正式称重和单据由本厂负责。云端及互联网故障不应进入本地称重或出单的同步调用链。总部资料维护权限暂不讨论；旧备份恢复后流水号倒退仍暂缓。

## 云端待建设的能力

| 能力 | 需覆盖的行为 | 依赖 |
| --- | --- | --- |
| 厂区与接入 | 厂区编码全局唯一；云端仅以厂区编码校验并归属同步数据 | 不使用厂端凭据或地磅编码；编码不是来源认证 |
| 总部基础资料 | 分类、物料、往来主体、联系人维护，以及状态、编码和引用规则；总部资料面向全部厂 | 字段与本地业务规格逐项对齐；不把总部权限方案当作已确认 |
| 完整资料读取 | 本地 Server 主动获取同一时点的完整资料，自动及主动同步复用同一逻辑；接收端只在完整校验成功后整体生效 | 实施前确定快照一致性、数据量、分页和失效处理，不能直接把普通变动中的管理列表逐页当作一致快照 |
| 单据变化接收 | 接收出单、作废、关联重开；厂端归属校验、变化去重、同单顺序及原单作废后重开；持久化成功后确认 | 双端先约定字段、稳定变化标识、错误与确认语义；云端单据与去重结果应共同提交 |
| 查询与统计 | 总部人员查询所有厂；按已收到的当前有效单及最终净重统计，区分方向，保留原资料编码 | 依赖单据接收及状态规则；页面提示可能存在同步滞后和短暂少计 |

云端厂区按用户要求不依赖厂区 ID；厂区编码作为跨系统归属依据，厂端地磅不进入同步归属。单据字段保存业务发生时的快照，不依赖总部当前资料存在或实时状态，不在读取时用新名称回填历史。云端按原编码统计，不做自动合并。

## 契约设计准备

在两端开始实现对接前，应把[业务边界契约](cloud-sync-contract.md)细化为双方一致的可调用契约，并完成样例及双方契约测试。至少逐项确定：

1. **资料集**：分类、物料、主体和联系人的字段、类型、必填与空值、稳定标识、关联与状态；参考本地业务规格中同名不同规格、多身份、联系人及停用等规则。定义完整集的边界、同一时点一致性、分页和中途变更处理。
2. **单据与变化**：厂区编码、单号与原单关联、业务方向、纸单信息、物料和供收方快照、两次确认时间、原始／最终重量、调整记录与联系信息；明确字段来源、缺失值、吨及 0.001 吨精度、时间格式。仅纳入已确认范围，不扩充照片、打印记录、承运方单据快照或纠错过程。
3. **确认与失败**：变化标识的作用范围、重复请求返回原确认、同一标识与不同内容冲突、顺序或原单依赖缺失、业务校验失败、临时失败、版本不兼容及重试语义。云端不可在事务提交前确认；未知结果可使用相同标识安全重试。
4. **接入**：无凭据厂区编码校验、编码变更、历史数据与原单归属。精确 HTTP 路由以接口设计目标为准，业务接口遵循云端 `/api/v1` 及统一响应约定。

基础资料接口及标识见[接口设计](weighbridge-sync-api-design.md)，第一版一次读取完整资料；单据字段及错误协议仍需双端核对。总部维护权限和恢复旧备份后流水号倒退不在本次设计中擅自决定。

## 建议工作顺序

1. **细化双端契约**：按上节列出字段及例外、编码归属、资料一致性和确认行为；用样例核对本地有效规格。验证：两端对同一份契约及失败语义达成一致。
2. **厂区接入和总部资料**：按现有 Go 分层与 Goose migration 建立必要模型和接口，提供总部资料管理及完整资料读取。验证：编码唯一、引用与停用、厂区归属，以及读取期间发生变更不会形成混合资料集。
3. **云端接收单据变化**：按已约定的契约实现事务、去重和顺序处理，保留各版本快照及关联。验证：重复与并发请求、确认丢失重试、编码互换、先作废再重开、前序失败和较旧变化不能覆盖较新状态。
4. **总部查询和统计**：接入现有前端路由与菜单体系，展示加载、错误、空数据和同步滞后提示。验证：所有厂查询、方向和最终净重、作废排除、重开不重复、原编码分组。
5. **与本地联调及断网验收**：由本地侧实现首次完整同步、周期及主动同步、持久化待上传变化、列表状态和管理员日志；云端配合契约测试。验证：断网持续出单、资料同步部分失败不生效、重启后自动补传、日志清空不影响待上传变化和状态。

总部管理写操作应遵循项目既有[业务与审计原子提交决策](../adr/0006-atomic-operation-audit.md)；不引入无实际需要的 MQ、Redis 或微服务。新增菜单组件须同时注册后端菜单与前端路由。涉及 schema 必须提交版本化 Goose migration，API 不自动迁移。

## 验证入口与限制

开发时按改动运行根目录 Taskfile 对应任务：后端 `task backend:check`，数据库集成使用 `task backend:integration`（需要 Docker）；前端运行 `task frontend:lint`、`task frontend:typecheck`、`task frontend:test`、`task frontend:build`。数据库结构变更使用 `task db:migrate` 于适当环境显式迁移；API 变更同步维护 Swagger 和契约测试。测试和故障演练使用隔离环境，不连接实际业务库。

上述命令和验收场景是要求，不代表全部已经通过；实际实现与验证结果应另行记录，不能由目标推定端到端完成。

## 云端实现状态

云端维护厂区编码和名称，通过编码检查启用状态并归属同步数据；版本 2 完整资料和单据变化接口不使用厂端凭据或地磅。改码保留历史数据归属和出单编码，历史编码不能分配给其他厂。接口和失败边界见[接口设计](weighbridge-sync-api-design.md)。厂端资料应用、事件持久化与重试、日志以及双端断网联调仍待厂端实现和验证。
